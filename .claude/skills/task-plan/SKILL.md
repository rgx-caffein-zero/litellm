# 実装計画の作成

コードを書く前に、以下の手順で計画を作り、ユーザーに提示してください。
計画の目的は、レビュアーが「なぜこの形になったか」を後から理解できるようにすることです。

## 1. 要求の確認

- ゴールと非ゴール（やらないこと）を 1〜3 行ずつ書く。
- 受け入れ基準を、検証可能な形で列挙する（「〜のとき〜になる」）。
- 曖昧な点があれば、ここで質問する。答えが得られない場合は、仮定として明記する。

## 2. 既存コードの調査

- `.harness/PROJECT.md` を読む。
- 変更対象と、その呼び出し元・呼び出し先を読む。
- **似た既存実装を最低 1 つ** 探し、次の点をメモする: ファイル配置、命名、エラー処理、ログ、テストの配置と書き方。
- 使う予定の外部 API・ライブラリ関数が実在し、想定どおりのシグネチャであることを確認する。

## 3. 設計

- 変更するファイルと、それぞれの変更内容を列挙する。
- 複数の設計案がある場合は、2 案を比較し、採用理由を書く。
- 公開インターフェース・データ形式・設定への影響と、互換性の扱いを書く。
- アーキテクチャに影響する判断なら、skill `adr-new` で ADR を作ることを計画に含める。
- 新しい依存を追加する場合は、理由と代替案を書く。

## 4. テスト計画

- 何を、どのレベル（ユニット / 結合 / E2E）でテストするかを書く。
- バグ修正の場合は、修正前に失敗する再現テストを最初のステップにする。

## 5. ステップ分割

- 各ステップが「ビルドとテストが通る」単位になるように分割する。各ステップがコミットの単位になる。
- リファクタリングが必要なら、振る舞いの変更より前の独立したステップにする。

## 出力形式

```
## ゴール / 非ゴール
## 受け入れ基準
## 調査結果（参考にした既存実装: path:line）
## 設計（変更ファイル一覧・採用案と理由）
## テスト計画
## ステップ
1. ...（コミットメッセージ案: `type(scope): subject`）
## 仮定とリスク
```

規模が大きい場合や設計に迷いがある場合は、計画をユーザーに確認してから実装に入ってください。
