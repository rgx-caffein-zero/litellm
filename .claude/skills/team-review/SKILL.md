# 独立レビュー

実装者は自分のコードの「読みにくさ」に気付けません。
このスキルでは、実装の経緯を知らないレビュアーに差分を見せ、チーム開発で別のメンバーがレビューするのと同じ状況を作ります。

## 1. 準備

- 先に skill `quality-gate` を実行し、品質ゲートが通っていることを確認する。
- 差分の範囲を決める（通常は `git merge-base HEAD main` から作業ツリーまで）。
- 変更の目的を 1〜3 行でまとめる。

## 2. レビュアーの起動

次のサブエージェントを **並行して** 起動します。

| サブエージェント | 起動する条件 |
| --- | --- |
| `code-reviewer` | 常に |
| `readability-reviewer` | 常に |
| `security-reviewer` | 外部入力、認証・認可、ファイル / ネットワーク I/O、SQL やシェルの組み立て、秘密情報、依存追加のいずれかを含む場合 |

各レビュアーに渡すのは **次の情報だけ** です。

```
目的: <1〜3 行>
差分の範囲: <例: main...HEAD と未コミットの変更>
```

実装中の試行錯誤、却下した案、「ここは意図的です」といった説明は **渡さないでください**。
先入観のない目で読んでもらうことが、このスキルの目的です。説明が必要に見える箇所は、コードかコメントで説明されているべき箇所です。

## 3. 指摘の集約

- 重複する指摘をまとめ、重大度順（must → should → question → nit）に並べる。
- レビュアー間で意見が割れた場合は、両方の意見を残す。

## 4. 対応

- `[must]`: すべて対応する。
- `[should]`: 原則対応する。見送る場合は理由を書く。
- `[question]`: コードかコメントを改善して答えるのが基本。説明が不要な場合のみ、報告で回答する。
- `[nit]`: 範囲内で簡単なものは対応してよい。

対応後は skill `quality-gate` を再実行してください。`[must]` があった場合は、対応後にもう一度このスキルを実行してください（最大 3 回。それでも `[must]` が残る場合は、ユーザーに相談する）。

## 5. 報告

```
## レビュー結果
| 重大度 | 件数 | 対応済み | 見送り |
| --- | --- | --- | --- |

## 対応した指摘
- [must] path:line — 指摘の要約 → 対応内容

## 見送った指摘と理由
- [should] path:line — 指摘の要約 → 見送った理由

## 人間のレビュアーに見てほしい点
- ...
```
