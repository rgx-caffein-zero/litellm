# ハーネスのセットアップ

目的は、このリポジトリの **既存の慣習** を明文化し、品質ゲートが確実に動く状態にすることです。
新しい規約を発明するのではなく、すでにあるものを記録してください。

## 1. 有効化と検出

```sh
scripts/harness/init.sh
scripts/harness/detect.sh
```

## 2. リポジトリの調査

次の情報を集めます。推測ではなく、ファイルの内容を根拠にしてください。

- README、既存のドキュメント、CONTRIBUTING、既存の CLAUDE.md / AGENTS.md / .cursorrules など
- マニフェスト（package.json, pyproject.toml, go.mod, Cargo.toml など）と lockfile
- フォーマッタ・リンタ・型チェッカーの設定ファイル
- 既存の CI 設定（どのコマンドで検証しているか）
- ディレクトリ構成と、代表的なソースファイル・テストファイル数個（命名、エラー処理、ログ、コメントの言語）
- 直近のコミットメッセージ（`git log --oneline -30`）

既存の CLAUDE.md や AGENTS.md に有用な情報がある場合は、`.harness/PROJECT.md` に移すか、ファイル間の重複を避ける方法をユーザーに提案してください（上書きしない）。

## 3. PROJECT.md の下書き

`.harness/PROJECT.md` の各節を埋めます。

- 分からない項目は空欄にせず「要確認: <何を確認すべきか>」と書く。
- 「コーディング規約（プロジェクト固有）」には、調査で確認できた慣習だけを書く。
- 用語集には、ドメイン固有の単語と、コード上での名前の対応を書く。
- 最後に、先頭の注記ブロックを削除する。

## 4. 品質ゲートの確定

```sh
scripts/harness/check.sh
```

- 検出されたコマンドが既存の CI と違う場合や、`(none)` のステップがある場合は、`.harness/project.env` に正しいコマンドを設定する（`scripts/harness/detect.sh --env` の出力が雛形になる）。
- 現時点で失敗するステップがある場合は、**このセットアップでは修正せず**、一覧にして報告する（既存の問題の修正は別タスク）。
- `HARNESS_REQUIRED_STEPS` が実態に合っているか確認する。

## 5. CI の確認

`.github/workflows/quality.yml` のツールチェーン設定（言語バージョンなど）が、このリポジトリに合っているか確認し、必要な変更を提案する。

## 6. 報告

```
## 検出されたスタック
## PROJECT.md で「要確認」とした項目
## 品質ゲートの状態（step ごとの結果と、既存の失敗）
## 推奨する次の作業
```

`.harness/` や CI の変更はユーザーの確認を求められます。変更内容を説明してから進めてください。
