# 開発ワークフロー

人間と AI エージェントが同じ手順で作業できるように、タスクの進め方を定義します。
目的は「誰が書いても、同じ品質で、レビューしやすい変更」を出すことです。

## 全体の流れ

```
理解 → 調査 → 計画 → 実装（小さく反復）→ 検証 → セルフレビュー → 独立レビュー → PR
                          ↑___________________________________|
                                   [must] 指摘があれば戻る
```

## 1. 理解

- 要求を 1〜3 行で言い直し、**ゴール** と **非ゴール**（やらないこと）を明確にする。
- 受け入れ基準を、検証可能な形で書き出す（「〜のとき〜を返す」）。
- 曖昧な点は推測で埋めない。確認できる相手がいれば質問し、いなければ仮定を明記して進める。

## 2. 調査

- 変更対象のコードと、その呼び出し元・呼び出し先を読む。
- **似た既存実装を最低 1 つ探し**、命名・ファイル配置・エラー処理・テストの書き方を確認する。新しいコードはそれに合わせる。
- 使おうとしているライブラリの API は、実際のコードか公式ドキュメントで存在とシグネチャを確認する。
- 既存のテストを実行し、作業前の状態（どのテストが通るか）を把握する。

## 3. 計画

次のいずれかに当てはまる場合は、実装前に計画を書く（Claude Code では skill `task-plan`）。

- 3 ファイル以上を変更する
- 公開 API・データ形式・設定を変更する
- 複数の設計案が考えられる
- 依存関係を追加する

アーキテクチャに影響する判断は ADR（`docs/adr/`、skill `adr-new`）に残す。

## 4. 実装

- 1 ステップごとに「ビルドが通り、テストが通る」状態を保つ。各ステップがそのままコミット単位になるのが理想。
- 可能ならテストを先に書く（特にバグ修正では、再現テストが失敗することを確認してから修正する）。
- リファクタリングが必要なら、振る舞いの変更より **先に**、別コミットで行う。
- 依頼範囲外の問題を見つけたら、直さずにメモして報告する。

## 5. 検証

```sh
scripts/harness/check.sh fix     # 自動修正できるものを直す
scripts/harness/check.sh         # すべての品質ゲートを通す
```

- 失敗したら、**根本原因** を直す。テストの削除・ルールの無効化・期待値の書き換えで通さない。
- 自動テストで確認しにくい変更（UI・CLI の出力・性能）は、手動で確認した手順と結果を記録する。

## 6. セルフレビュー

差分全体（`git diff <base>...HEAD`）を、`docs/harness/REVIEW_CHECKLIST.md` に沿って自分で読み直す。
特に次を確認する。

- 不要な変更・デバッグ出力・コメントアウトしたコードが残っていないか
- 名前とコメントが、最終的な実装と一致しているか
- PR の説明だけで、レビュアーが変更の意図を理解できるか

## 7. 独立レビュー

実装の経緯を知らない第三者の目でレビューする。AI エージェントの場合は、レビュー用サブエージェントを使う（skill `team-review`）。

- レビュアーには **目的と差分の範囲だけ** を渡す。実装中の試行錯誤や言い訳は渡さない（先入観を与えないため）。
- `[must]` はすべて対応する。`[should]` は対応するか、見送る理由を残す。
- 対応後は、再度検証とレビューを行う。

## 8. PR

- `.github/pull_request_template.md` を埋める（skill `pr-ready`）。
- CI がすべて成功していることを確認する。
- 人間のレビュアーの承認を得てからマージする。

## ブランチ運用（デフォルト）

`.harness/PROJECT.md` に別の指定がなければ、次の運用とします。

- `main` は常にリリース可能な状態に保つ。直接 push しない。
- 作業ブランチ名: `<type>/<短い説明>`（例: `feat/order-export`, `fix/login-timeout`）。`<type>` はコミット規約と同じ。
- マージ方法: squash merge を推奨。PR タイトルがそのままコミットメッセージになるため、PR タイトルもコミット規約に従う。

## 困ったとき

| 状況 | 行動 |
| --- | --- |
| 要求が曖昧 | 質問する。答えが得られない場合は、仮定を明記して最小限の実装に留める |
| 既存コードの慣習が規約と矛盾 | 既存の慣習に合わせ、規約との差を報告する |
| 品質ゲートが自分の変更と無関係な理由で失敗 | 修正せずに報告する（無関係な修正を混ぜない） |
| 同じ失敗を 3 回繰り返した | 作業を止め、状況・試したこと・仮説を報告して相談する |
