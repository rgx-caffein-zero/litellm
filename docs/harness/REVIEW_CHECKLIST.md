# レビューチェックリスト

人間のレビュアーと、レビュー用サブエージェントの両方が使うチェックリストです。
フォーマッタやリンタで検出できる指摘はしないでください（それは CI の仕事です）。

## 指摘の重大度

| ラベル | 意味 | マージ前の対応 |
| --- | --- | --- |
| `[must]` | バグ、セキュリティ問題、データ破損、仕様違反、テスト欠如、規約違反 | 必須 |
| `[should]` | 読みやすさ・保守性・一貫性の明確な改善 | 原則対応。見送る場合は理由を返信 |
| `[nit]` | 好みに近い細かな改善 | 任意 |
| `[question]` | 意図の確認 | 回答必須（コードかコメントで答えるのが望ましい） |

指摘には必ず **場所（ファイル:行）**、**理由**、**改善案** を含めてください。
「一貫性がない」と指摘する場合は、比較対象の既存コードの場所を示してください。

## 1. 目的と範囲

- [ ] 変更の目的が PR の説明から分かる。
- [ ] 目的と関係のない変更が混ざっていない。
- [ ] 要求を満たしている。過剰な実装（使われない汎用化・将来のための拡張点）がない。

## 2. 正しさ

- [ ] 境界値・空・null / nil・重複・大量データ・不正入力で正しく動く。
- [ ] エラー経路が正しく処理され、握りつぶされていない。
- [ ] 並行処理・再実行・途中失敗で状態が壊れない（冪等性・トランザクション）。
- [ ] リソースが確実に解放される。
- [ ] 時刻・タイムゾーン・ロケール・文字コードの扱いが正しい。

## 3. 読みやすさ（初見の人の視点）

- [ ] 名前だけで役割が分かり、実装を読まなくても使い方が推測できる。
- [ ] 関数・モジュールの責務が 1 つに絞られている。
- [ ] ネストが深すぎず、処理の流れを上から追える。
- [ ] 自明でない判断には「なぜ」のコメントがある。古いコメントやコメントアウトしたコードがない。
- [ ] 読んでいて「驚き」がない（名前と振る舞いが一致し、隠れた副作用がない）。

## 4. 一貫性

- [ ] 周囲のコードと同じ命名・構造・エラー処理・ログの書き方になっている。
- [ ] 同じことをする既存の仕組み（ユーティリティ・ヘルパー・共通処理）を再発明していない。
- [ ] ディレクトリ配置とファイル名が既存の慣習に沿っている。
- [ ] 用語が `.harness/PROJECT.md` の用語集と一致している。

## 5. テスト

- [ ] 振る舞いの変更にテストがある。バグ修正に再現テストがある。
- [ ] テストが実装の詳細ではなく振る舞いを検証している。
- [ ] 異常系・境界値のテストがある。
- [ ] テスト名から、何を検証しているかが分かる。
- [ ] テストが独立していて、決定的（フレーキーでない）。

## 6. 設計と保守性

- [ ] 依存の方向が適切で、循環がない。I/O とロジックが分離されている。
- [ ] 公開範囲が最小限になっている。
- [ ] 公開 API・データ形式の変更について、互換性への影響が明記されている。
- [ ] 新しい依存の追加に、正当な理由がある。

## 7. セキュリティ

- [ ] 外部入力が境界で検証されている。
- [ ] SQL・シェル・HTML・パスへの埋め込みが安全な方法で行われている。
- [ ] 認可チェックが漏れていない。
- [ ] 秘密情報・個人情報がコード・ログ・エラーメッセージ・テストデータに含まれていない。

## 8. ドキュメントと運用

- [ ] 利用者に見える変更が README やドキュメントに反映されている。
- [ ] 設定項目・環境変数の追加が文書化されている。
- [ ] ログが調査に十分で、かつ過剰でない。
- [ ] 抑制コメント（lint / 型チェックの無効化）がある場合、理由が書かれている。
