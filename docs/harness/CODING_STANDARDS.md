# コーディング規約（言語非依存）

この規約は特定の言語やフレームワークに依存しない原則をまとめたものです。
各言語の公式スタイルガイドとフォーマッタ・リンタの結果は、この規約より優先します（機械で判定できるものは機械に任せる）。
数値の基準は「目安」です。超える場合は、超える理由をレビュアーが理解できるようにしてください。

## 0. 判断の優先順位

1. **正しさ** — 仕様どおりに動き、エッジケースで壊れない。
2. **読みやすさ** — 初見の人が意図を理解できる。
3. **一貫性** — 周囲のコードと同じ書き方をしている。
4. **変更しやすさ** — 次の変更者が安全に手を入れられる。
5. **性能** — 計測で必要性が示された場合に最適化する。

巧妙さよりも明快さを選んでください。「短い」ことは読みやすさの理由になりません。

## 1. 命名

- 名前は **何であるか / 何をするか** を表す。型や実装方法ではなく、役割を表す（`userList` より `activeUsers`）。
- 関数・メソッドは動詞で始める（`calculateTotal`, `fetch_orders`）。真偽値は `is` / `has` / `can` / `should` などで問いの形にする。
- 略語は、その分野で一般的なもの（`id`, `url`, `http`）以外は使わない。1 文字の名前はごく短いループ変数や慣習的な用途（数式の `x`, `y`）に限る。
- 同じ概念には同じ単語を使う。`fetch` / `get` / `load` や `remove` / `delete` を同じ意味で混在させない。用語は `.harness/PROJECT.md` の用語集に合わせる。
- 単位や形式が曖昧な値には、名前に含める（`timeoutMs`, `priceCents`, `createdAtUtc`）。
- 否定形の真偽値（`isNotEnabled`）は避ける。

## 2. 関数とモジュールの設計

- **1 つの関数は 1 つのことをする。** 説明に「〜して、さらに〜する」が必要なら分割を検討する。
- 関数の長さの目安は 40 行以内、引数は 4 個以内。超える場合は、引数オブジェクトや分割を検討する。
- 抽象度を揃える。高レベルの処理の流れと、低レベルの詳細（文字列操作やバイト処理）を同じ関数に混在させない。
- モジュールの公開範囲は最小にする。外部から使われないものは公開しない。
- 依存の方向を一方向に保つ。循環依存を作らない。ドメインロジックは I/O（DB・HTTP・ファイル・時刻・乱数）から分離し、テスト可能にする。
- 似たコードが 3 回現れるまでは、無理に共通化しない。誤った抽象化は重複より高くつく。
- マジックナンバー・マジック文字列は、意味のある名前の定数にする。

## 3. 制御フロー

- ネストの深さの目安は 3 段まで。早期リターン（ガード節）で浅くする。
- 条件式が複雑な場合は、意味のある名前の変数や関数に切り出す。
- `else` の後に処理が続くより、異常系を先に処理して正常系をインデントの浅い位置に置く。
- フラグ引数（`process(data, true)`）で関数の振る舞いを切り替えない。関数を分けるか、名前付きの選択肢にする。

## 4. エラー処理

- エラーを握りつぶさない。空の catch / except、無視された戻り値は禁止。意図的に無視する場合は理由をコメントする。
- エラーは **扱える場所で扱う**。扱えない層では、文脈を付け加えて上に伝える（何をしようとして失敗したか）。
- エラーメッセージには、原因の特定に必要な情報（対象の ID、入力の要約）を含める。ただし秘密情報や個人情報は含めない。
- 想定内の失敗（入力不正・見つからない）と、想定外の失敗（バグ・環境異常）を区別する。
- 外部から来る入力（ユーザー入力・ファイル・ネットワーク・環境変数）は、境界で検証する。内部では検証済みの型や値を受け渡す。
- リソース（ファイル・接続・ロック）は、言語の仕組み（`with`, `defer`, `using`, `try-with-resources`, RAII など）で確実に解放する。

## 5. 状態と副作用

- 可能な限り不変（immutable）なデータを使う。引数として受け取った値を変更しない。
- グローバルな可変状態を作らない。必要なら明示的に注入する。
- 副作用のある関数とない関数を名前と構造で区別する。
- 時刻・乱数・環境変数・設定は、直接参照せず注入可能にする（テストで固定できるようにする）。
- 並行処理では、共有状態とその保護方法を明示する。

## 6. コメントとドキュメント

- コメントには **なぜ** を書く。**何を** しているかはコードで表現する。
- 次のものには必ずコメントを書く:
  - 自明でない設計判断、トレードオフ、却下した代替案
  - 外部仕様・バグ回避・性能上の理由による一見不自然なコード（参照先 URL や Issue 番号を添える）
  - 公開 API（目的・引数・戻り値・エラー・使用例）
- コードと食い違うコメントはバグとして扱う。コードを変えたらコメントも更新する。
- コメントアウトしたコードを残さない。履歴は Git にある。
- `TODO` / `FIXME` には担当または Issue 番号を付ける（`TODO(#123): ...`）。
- コメントの言語は `.harness/PROJECT.md` の指定に従う。指定がなければ周囲のコードに合わせる。
- 利用者に見える変更（機能・設定・CLI・API）は、README や関連ドキュメントを同じ変更で更新する。

## 7. テスト

- 振る舞いを変える変更には、その振る舞いを検証するテストを付ける。バグ修正には、修正前に失敗する再現テストを付ける。
- テストは **実装ではなく振る舞い** を検証する。内部構造を変えても、振る舞いが同じならテストは壊れないようにする。
- テスト名は「条件」と「期待結果」が分かるようにする（`returns_empty_list_when_no_orders_exist`）。
- 1 つのテストでは 1 つの振る舞いを検証する。Arrange / Act / Assert を視覚的に分ける。
- テストは独立させる。実行順序・共有状態・時刻・ネットワークに依存させない。
- 正常系だけでなく、境界値・空・null / nil・不正入力・エラー経路をテストする。
- テストコードも本番コードと同じ品質基準で書く。ただし、テストでは DRY より読みやすさを優先してよい。
- フレーキーなテストを放置しない。リトライで隠さず原因を直す。

## 8. 依存関係

- 新しい依存を追加する前に、標準ライブラリや既存の依存で解決できないか確認する。
- 追加する場合は、PR に理由・代替案・メンテナンス状況・ライセンスを書く。
- バージョンは lockfile で固定する。lockfile は必ずコミットする。
- 依存の更新は、機能変更とは別のコミット・PR にする。

## 9. ログと可観測性

- ログレベルを使い分ける（error: 対応が必要 / warn: 想定外だが継続可能 / info: 主要な業務イベント / debug: 調査用）。
- ログは機械で検索できる形にする（構造化ログが使えるなら使う）。
- 秘密情報・個人情報・トークン・リクエスト本文全体をログに出さない。
- デバッグ用の一時的な出力（`print`, `console.log` など）を残さない。

## 10. セキュリティ

- 外部入力は信頼しない。SQL・シェル・HTML・パスなどに埋め込む際は、パラメータ化やエスケープなどの専用の仕組みを使う。文字列連結で組み立てない。
- 認証・認可のチェックは、サーバー側（信頼できる側）で毎回行う。
- 秘密情報はコードに書かず、環境変数やシークレット管理の仕組みから読む。
- 暗号処理は自作せず、標準的なライブラリを推奨設定で使う。
- 最小権限の原則に従う（ファイル権限、DB 権限、トークンのスコープ）。

## 11. 性能

- 推測で最適化しない。必要性は計測で示す。
- ただし、明らかな非効率（ループ内の I/O、N+1 クエリ、不要な全件読み込み、二重ループでの線形探索）は最初から避ける。
- 性能のために可読性を犠牲にした箇所には、計測結果や理由をコメントする。

## 12. 公開 API と互換性

- 公開されているインターフェース（API・CLI・設定ファイル・データ形式）を変更する場合は、互換性への影響を明示する。
- 破壊的変更は、コミットメッセージに `!` または `BREAKING CHANGE:` を付け、移行方法をドキュメントに書く。
- 可能であれば、非推奨（deprecation）の期間を設けてから削除する。

## 13. 変更の粒度

- 1 つの PR は 1 つの目的に絞る。目安は差分 400 行以内。
- リファクタリングと振る舞いの変更は、コミットを分ける。
- 自動生成ファイルやフォーマットのみの変更は、別コミットにする。
- 大きな設計判断は、実装前に ADR（`docs/adr/`）で合意する。
