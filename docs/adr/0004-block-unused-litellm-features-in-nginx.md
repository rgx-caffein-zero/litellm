# 0004. 無効化の設定がない LiteLLM の機能は nginx で遮断する

- ステータス: 提案中
- 日付: 2026-10-31
- 決定者: LiteLLM 導入担当
- 関連: [requirements.md](../requirements.md)（R6・R7・C7）、`nginx/default.conf`、`docker-compose.yml`

## 背景

LiteLLM 1.106.6 には、この構成で使わない機能が含まれている。

- Moyai: 外部サービスと接続し、仮想キーを発行する。`/moyai/connect/exchange` は、LiteLLM が認証なしで受け付けるルート（`public_routes`）に含まれている。
- Lens: 外部サービスへトレースを送り、評価する。
- Auto Router: リクエストの難易度でモデルを振り分ける。プリセットを GitHub から取得する。

イメージのソースを確認した範囲では、これらの機能を無効にする環境変数や `config.yaml` の設定はない。
Moyai のルーターは常に登録される。Lens と Auto Router は、ルートが初めて呼ばれたときに読み込まれるだけで、エンドポイントは残る。

一方、API ドキュメントと外部からの取得は、LiteLLM の環境変数（`NO_DOCS` など、`LITELLM_LOCAL_*`）で止められる。

## 検討した選択肢

### 選択肢 A: 何もしない（管理者の端末からだけ使える状態のまま）

- 概要: 既存の nginx の設定（C7）で、一般の PC からは届かない。
- 利点: 変更がない。
- 欠点: 管理者の端末からは使えてしまう。管理 UI の操作ミスで外部サービスに接続し、キーを発行するおそれがある。

### 選択肢 B: LiteLLM のイメージやソースを変更する

- 概要: 該当するルーターを登録しないようにパッチを当てたイメージを作る。
- 利点: エンドポイント自体がなくなる。
- 欠点: LiteLLM を更新するたびにパッチを当て直す必要がある。公式イメージを digest で固定する方針と合わない。

### 選択肢 C: nginx で遮断する

- 概要: 該当するパスに、接続元にかかわらず 404 を返す。
- 利点: 公式イメージをそのまま使える。既存のアクセス制御と同じ場所で管理でき、`tests/nginx.test.sh` で検証できる。
- 欠点: パスは LiteLLM の実装に依存するため、更新でパスが変わると遮断できなくなる。管理 UI のメニューには残る。

## 決定

選択肢 C を採用する。LiteLLM の設定で止められるもの（API ドキュメント、外部からの取得）は LiteLLM の環境変数で止め、設定がないもの（Moyai、Lens、Auto Router）だけを nginx で遮断する。
nginx は正規化後のパスで location を選ぶため、`%XX` や `..` を含むパスでも遮断できる。

Enterprise 機能は、ライセンス（`LITELLM_LICENSE`）を設定しない限り使えず、ライセンス確認の通信も発生しないため、追加の設定はしない。

## 影響

- 良い影響: 外部サービスとの連携が、管理者の操作でも起きなくなる。
- 悪い影響・受け入れるトレードオフ: 管理 UI のメニューに Moyai や Lens が残り、開くと 404 になる。管理 UI の API Reference の画面は、`/openapi.json` を無効にしたため使えない。
- 必要になる作業: LiteLLM の更新時に、リリースノートで機能の追加やパスの変更を確認する（[operations.md](../operations.md)）。

## 見直しの条件

- LiteLLM に、機能ごとに無効にする設定が追加されたとき。
- Moyai、Lens、Auto Router のいずれかを使うことになったとき。
