# 0002. 用途と範囲を制限した自前のルート CA で HTTPS 化する

- ステータス: 承認済み
- 日付: 2026-10-31
- 決定者: LiteLLM 導入担当
- 関連: [requirements.md](../requirements.md)（C1）

## 背景

Claude Desktop のサードパーティ推論（Gateway）は、HTTPS で公開されたゲートウェイを前提とする。既存の社内 LiteLLM は HTTP のため設定できなかった。
社内にはサーバー証明書を発行できる CA がなく、サーバーへは IP アドレスで接続する（DNS 名がない）。
そのため、自前で発行した証明書を各 PC に手動でインストールして信頼させる必要がある。

一方で、PC の「信頼されたルート証明機関」に入れた CA は、その PC が信頼するあらゆる証明書の発行元になれる。
CA の秘密鍵が漏れると、一般の Web サイトのなりすましや、コード署名・メール署名の偽造に悪用されるおそれがある。

## 検討した選択肢

### 選択肢 A: サーバー証明書を自己署名し、それを各 PC に入れる

- 概要: CA を作らず、サーバー証明書そのものを自己署名して信頼させる。
- 利点: 手順が最も少ない。
- 欠点: サーバー証明書を更新する（825 日ごと、または IP アドレスの変更時）たびに、全 PC へ配布し直す必要がある。証明書に制約を付けられない。

### 選択肢 B: 制約のない自前のルート CA を作る

- 概要: 一般的な手順で CA を作り、サーバー証明書を発行する。
- 利点: サーバー証明書を更新しても PC 側の作業は不要。
- 欠点: CA の鍵が漏れると、任意の Web サイトやコード署名の証明書を偽造できる。

### 選択肢 C: 用途と範囲を制限した自前のルート CA を作る

- 概要: 選択肢 B の CA 証明書に、Extended Key Usage（serverAuth のみ）と Name Constraints（指定した IP アドレス範囲のみ。DNS 名・メールアドレス・URI は実在しない `.invalid` だけを許可）を入れる。
- 利点: サーバー証明書の更新で PC 側の作業が不要なまま、鍵が漏れたときの被害を「指定した IP 範囲のサーバーのなりすまし」に限定できる。
- 欠点: サーバーの IP アドレスが許可範囲の外に変わると、CA を作り直して全 PC に配布し直す必要がある。サーバー証明書の CN をホスト名に見えない文字列にする必要がある（OpenSSL などは、ホスト名に見える CN を DNS 名として制約と照合するため）。

## 決定

選択肢 C を採用する（`scripts/certs/create-ca.sh`）。

PC への配布は手動で行うため、配布の回数を減らせる CA 方式（B または C）が望ましい。
そのうえで、全社の PC に入る証明書なので、鍵が漏れたときの被害を限定できる C を選ぶ。
制約の効果は `tests/certs.test.sh` で検証している（他の IP・DNS 名・メールアドレス・クライアント認証の証明書が拒否されること）。

## 影響

- 良い影響: サーバー証明書の更新では PC 側の作業が不要。CA の鍵が漏れても、一般の Web サイトやコード署名の偽造には使えない。
- 悪い影響・受け入れるトレードオフ:
  - 許可範囲を `/32` にすると、サーバーの IP アドレスが変わるたびに CA の再配布が必要になる。
  - Windows や Claude Desktop が CA の制約をどう扱うかは、PoC（P1）で確認する。
- 必要になる作業: CA の秘密鍵をサーバーから退避して保管する運用（[setup.md](../setup.md)）。

## 見直しの条件

- 社内 CA や、正規の証明書を発行できる環境（社内 DNS 名と ACME など）を使えるようになったとき。
- Claude Desktop が、制約付きの CA で発行した証明書を受け付けないことが PoC で分かったとき。
