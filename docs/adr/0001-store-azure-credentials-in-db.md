# 0001. Azure OpenAI の認証情報を管理 UI で登録し DB に暗号化して保存する

- ステータス: 承認済み
- 日付: 2026-10-31
- 決定者: LiteLLM 導入担当
- 関連: [requirements.md](../requirements.md)（R2・R4）

## 背景

要件では「機密情報は `.env` に分ける」ことと、「案件の追加などの運用を管理 UI だけで完結させ、コンテナの設定を変えない」ことを求めている。

Azure OpenAI のリソースは案件ごとに作られるため、案件の数だけ API キーとエンドポイントがある。
すべてを `.env` に置くと、案件を追加するたびに `.env` と `config.yaml` を編集し、コンテナを再起動する必要がある。2 つの要件が両立しない。

## 検討した選択肢

### 選択肢 A: 管理 UI で登録し、DB に暗号化して保存する

- 概要: `STORE_MODEL_IN_DB=True` とし、Azure のモデルと認証情報を管理 UI で登録する。認証情報は LiteLLM が `LITELLM_SALT_KEY` で暗号化して PostgreSQL に保存する。
- 利点: 案件の追加が管理 UI だけで完結し、再起動も不要。コード・`docker-compose.yml`・`config.yaml` に機密情報が入らない。
- 欠点: 機密情報の保存先が `.env` と DB の 2 か所になる。`LITELLM_SALT_KEY` を失うと、登録済みの認証情報を復号できない。

### 選択肢 B: `.env` に置き、`config.yaml` の `credential_list` から参照する

- 概要: 案件ごとに `AZURE_<案件>_API_KEY` などを `.env` に追加し、`config.yaml` で `os.environ/...` として参照する。
- 利点: 機密情報の保存先が `.env` だけになる。設定がファイルとして残り、レビューできる。
- 欠点: 案件の追加のたびにサーバー上のファイル編集と再起動が必要。再起動中はすべての案件の利用が止まる。

## 決定

選択肢 A を採用する。

案件の追加は頻繁に発生し、そのたびにファイルの編集と再起動が必要になる運用は避けたい。
選択肢 A でも、「機密情報をコードや設定ファイルに書かない」という R2 の趣旨は守れる。DB には暗号化して保存される。

`.env` に置くのは、起動に必要な機密情報（マスターキー、ソルトキー、DB のパスワード、AWS のアクセスキー）に限る。
AWS は全案件で 1 つのアカウントを共有するため、`.env` に置いても案件の追加時に変更は発生しない。

## 影響

- 良い影響: 案件の追加・削除が管理 UI だけで完結する（[operations.md](../operations.md)）。
- 悪い影響・受け入れるトレードオフ:
  - `LITELLM_SALT_KEY` は変更できない。`.env` を DB のバックアップとセットで保管する必要がある。
  - 管理 UI にログインできる人（マスターキーを持つ人）は、Azure の認証情報を登録・置き換えできる。マスターキーは管理者だけで管理する。
- 必要になる作業: `.env` のバックアップ手順の整備（[operations.md](../operations.md#バックアップとリストア)）。

## 見直しの条件

- 外部のシークレット管理サービス（AWS Secrets Manager、Azure Key Vault など）を使えるようになったとき。
- 案件の数が少なく、追加の頻度も低いことが分かったとき。
