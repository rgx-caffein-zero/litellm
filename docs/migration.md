# 現行環境からの移行手順

現行（移行元）の LiteLLM の DB を、この構成（移行先）にコピーする手順です。
チーム・キー・予算・利用額・管理 UI で登録したモデルと認証情報が引き継がれます。

移行元には書き込まず、停止も再起動もしません。DB のスキーマの更新（マイグレーション）は、移行先の LiteLLM が起動時に移行先の DB だけに行います。

> [!WARNING]
> 移行先の LiteLLM の接続先（`DATABASE_URL`）を、移行元の DB にしないでください。
> LiteLLM は起動時に接続先の DB をマイグレーションするため、移行元の DB が新しいバージョンのスキーマに書き換わります。

## 確認済みのバージョン

| | LiteLLM | PostgreSQL |
| --- | --- | --- |
| 移行元 | v1.83.14-stable.patch.3 | 15 |
| 移行先 | 1.106.6 | 17.8 |

この組み合わせで、ダンプ・リストア・起動時のマイグレーションの後、移行元で発行したキーで推論 API に接続できること、暗号化して保存された認証情報（Azure の API Base）を復号できることを確認しています。

## 1. ダンプする（移行元のサーバー）

[scripts/migration/dump-db.sh](../scripts/migration/dump-db.sh) だけを移行元のサーバーにコピーして実行します（リポジトリ全体は不要です）。
利用の少ない時間帯に実行してください。

```sh
docker ps    # DB と LiteLLM のコンテナ名を確認する
./dump-db.sh --db-container <DB のコンテナ> --litellm-container <LiteLLM のコンテナ>
```

スクリプトは、移行元に影響を与えないよう次のようにしています。

- `pg_dump` は読み取り専用で動き、LiteLLM の通常の読み書きを止めない。
- 開始時にロックをすぐに取れなければ、待たずに失敗する。
- 出力先の空き容量が DB のサイズの 2 倍より少なければ中止する。容量が足りない場合は、`--output` で別のディスクを指定する。
- Ctrl-C で中断すると、移行元の DB で動いている pg_dump の接続も終了させ、不完全なファイルを削除する。

> [!WARNING]
> ダンプ中は、移行元の LiteLLM を再起動しないでください。
> pg_dump はダンプが終わるまで全テーブルのロックを持ち続けます。LiteLLM が起動時のマイグレーションでテーブル定義を変更しようとすると、変更がロックを待ち、その後ろに通常のリクエストが並んで、**移行元が応答しなくなります**。
> 移行元が応答しなくなったら、すぐに Ctrl-C でダンプを中断してください。中断の表示に警告が出た場合は、次のコマンドで pg_dump の接続が残っていないことを確認します（0 なら残っていません）。
>
> ```sh
> docker exec <DB のコンテナ> psql -U <DB のユーザー> -d <DB 名> -Atc \
>   "SELECT count(*) FROM pg_stat_activity WHERE application_name LIKE 'litellm-migration-dump-%'"
> ```

利用ログ（管理 UI の Logs の履歴）が不要な場合は `--exclude-spend-logs` を付けると、ダンプが小さく速くなります。チームとキーの利用額は別のテーブルにあるので、予算の残りは引き継がれます。

実行すると、主なテーブルの件数と、ダンプの SHA-256 が表示されます。両方を、移行元の画面から直接控えてください。

ソルトキーの確認は、コンテナの環境変数だけを見ます。移行元の `config.yaml` の `environment_variables` でソルトキーを設定している場合は、表示に関係なく、その値を使ってください。

## 2. ソルトキーを合わせる（移行先）

手順 1 の「LITELLM_SALT_KEY の設定」の表示に従って、移行先の `.env` の `LITELLM_SALT_KEY` を設定します。

| 移行元の LITELLM_SALT_KEY | 移行先の LITELLM_SALT_KEY に設定する値 |
| --- | --- |
| 設定あり | 移行元の `LITELLM_SALT_KEY` と同じ値 |
| 設定なし | 移行元の `LITELLM_MASTER_KEY` の値（ソルトキーがない場合、LiteLLM はマスターキーで暗号化するため） |

値が違うと、管理 UI で登録した認証情報を復号できません。
`LITELLM_MASTER_KEY` は移行元と違っても構いません（キーはハッシュで保存されているため、移行元で発行したキーはそのまま使えます）。

## 3. リストアする（移行先のサーバー）

ダンプを、scp などの暗号化された経路で移行先のサーバーにコピーし、所有者だけが読めるようにします。
リポジトリのディレクトリで、手順 1 で控えた SHA-256 を指定して実行します。

```sh
chmod 600 <ダンプファイル>
scripts/migration/restore-db.sh <ダンプファイル> --sha256 <手順 1 で控えた SHA-256>
```

SHA-256 が一致しなければ、何もせずに終了します。
リストアは DB の管理者の権限で行うので、途中で差し替えられたダンプを入れると、DB のコンテナで任意の処理が動きます。
そのため、SHA-256 はダンプと同じ経路（同じフォルダやメールなど）で受け渡さないでください。

docker の接続先（`DOCKER_HOST` や `docker context`）は切り替えずに実行してください。スクリプトが確かめるのは、接続先のホストのコンテナとボリュームだけです。

> [!CAUTION]
> 移行先の DB の内容はすべて削除されます。移行先で作ったチームやキーは残りません。

スクリプトは次の順に処理し、LiteLLM と nginx を停止したまま終了します。

1. 同じプロジェクト名のコンテナが別のディレクトリにあれば中止する（同じホストに移行元がある場合に、移行元を操作しないため）。
   中止された場合は `COMPOSE_PROJECT_NAME=<別の名前>` を付けて実行する。
   コンテナがなく、同じプロジェクト名のボリュームだけが残っている場合も、どの環境のものか確かめられないので中止する。
2. LiteLLM と nginx を止め、DB を作り直してリストアする。途中で失敗した場合、DB は空のままになる。
3. テーブルの件数、DB に保存された設定、モデル名の重複を表示する。

表示を見て、次を確認してください。

- テーブルの件数が、手順 1 の表示と同じである。
- DB に保存された設定に通知（Slack・メールなど）やコールバックがあれば、移行先からも送られる。不要なら、起動後に管理 UI で無効にする。
- モデル名の重複がある場合、LiteLLM は同じ名前のモデルの間で負荷分散する。起動後に、管理 UI で DB 側のモデルを削除する。

## 4. 起動して確認する（移行先）

`.env` を変更したので、新しいシェルで実行します（[operations.md](operations.md#管理-ui-と管理-api) の注意を参照）。

```sh
docker compose up -d --wait
docker compose logs litellm | grep -i -E 'migrat|error'
set -a; . ./.env; set +a
LITELLM_API_KEY="$LITELLM_MASTER_KEY" scripts/smoke-test.sh https://<サーバーの IP アドレス>
```

管理 UI で、チーム・キー・モデルが移行元と同じであること、Azure のモデルを開いてエラーにならないことを確認します。

## 注意点

- 移行先には移行元と同じキーが入るため、移行元のキーで移行先も使えます。切り替えるまでは、移行先を利用者に案内しないでください。
- 移行先から推論すると、移行元と同じ AWS・Azure の認証情報を使います。クォータと請求は移行元と共有です。
- コピーは実行した時点のものです。本番を切り替えるときは、移行元の利用を止めてから、手順 1 からやり直します。
- 移行元の `config.yaml` に書いたモデルは DB にないため、移行されません。必要なら、管理 UI で登録します。
- ダンプには、キーのハッシュや暗号化された認証情報が含まれます。移行が終わったら、移行元と移行先の両方でダンプを削除してください。
